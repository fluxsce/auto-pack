# 正式版本上线后的补丁发版与 FTP 推送

适用于**已对外发布的正式版本**（例如正式 Tag `V9.0.0-P01`）。后续缺陷修复、修订版本构建与公司 FTP 环境更新，请按**两个角色**分工执行，避免版本号、分支、产物与远程环境不一致。

## 命名对照（示例：V9.0.0-P01）

| 含义 | 示例 | 说明 |
|------|------|------|
| 正式版 Git Tag | `V9.0.0-P01` | 正式上线时打的 Tag，**发布后不再修改**，仅作基线 |
| Release 发版分支 | `release/V9.0.0-P01` | 在该分支上提交、合并补丁代码 |
| 修订 Tag | `V9.0.0-P01-01`、`V9.0.0-P01-02`… | 每次补丁递增 `-01`、`-02`，用于本次发版与构建 |

---

## 一、项目开发 / 客服同学（提单与信息确认）

在提交补丁需求或协调修复前，请明确以下信息，便于修复同学选对版本与 FTP 目标。

1. **指定当前环境使用的版本号**
   - 在运行环境中打开 **【环境监控】→【应用扩展信息】**，查看并记录当前部署的**具体版本号**（如 `V9.0.0-P01` 或修订版 `V9.0.0-P01-01`）。
   - 工单/说明中必须写明该版本号，避免按错误基线修复或推送到错误环境。

2. **说明项目所在公司的 FTP 推送路径**
   - 写明目标公司/环境对应的 **FTP 推送目录**（如 `/开发/某某项目/update` 或完整远程包路径）。
   - 若各工程路径不同，按工程分别说明；修复同学在「自动发版」对话框中为**需要推送的工程**单独配置或确认路径。

---

## 二、修复同学（自动打包工具操作）

补丁代码合并完成后，使用本仓库 **自动打包控制台** 完成发版、构建与公司 FTP 推送。

1. **在 Release 分支上提交并合并补丁**  
   基于发版分支（如 `release/V9.0.0-P01`）提交并合并补丁代码；不要在未对应的 `develop` / `main` 上直接改已发布产品线。

2. **工作空间「自动发版」（打修订 Tag）**  
   路径：**工程管理** → 选择工作空间 → 批量操作 → **自动发版**。  
   填写发版分支（如 `release/V9.0.0-P01`）与本次修订 Tag（如 `V9.0.0-P01-01`，第二次小修为 `-02`）；按需更新 POM；发版说明可补充客服单号。发版成功后，工程 Git 分支将同步为 `refs/tags/{修订Tag}`。

3. **选择需要推送的工程并 FTP 推送**  
   在同一对话框下半部分 **构建与远程推送**：开启「发版成功后自动构建」「构建完成后 FTP 推送」（建议）；在 **推送工程** 中勾选本次需推到公司 FTP 的工程（不必全选）；FTP 环境、推送路径与客服提供的一致；变更说明写入 `updateNote.txt`（远程已有内容时**末尾追加**）。执行后右侧日志展示：发版 → 构建 → 推送；产物为 `target` 下 **war / jar** 及 `updateNote.txt`。单工程也可在 **工程详情 → 工程目录** 对 war/jar 使用 **远程推送**。

**控制台入口：** 环境管理 → FTP；工程管理 → 工作空间 → 自动发版；工程详情 → 工程目录 → 远程推送；任务面板 → 版本发布与补丁流程。

**注意：** 正式版 Tag（如 `V9.0.0-P01`）勿改，仅新增修订 Tag；推送前再次核对版本号与 FTP 路径；`updateNote.txt` 不做备份仅追加，更新包在 BAK 目录无同名备份时才备份（`BAK/YYYYMMDDHHmmssSSS`）。
